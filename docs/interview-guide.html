PrimeX EventGate

A safety gate for event-driven systems. Before a team changes the shape of an event, EventGate checks which other services depend on it, tells you exactly what will break, and blocks the release if it's unsafe.

01 Explain it like I'm 5

Use this first in any interview. Start simple, then go deeper only if they ask.

🍽️

The restaurant analogy

A kitchen (the producer) prints order tickets. Waiters, the cashier and the stock-keeper (the consumers) all read those tickets.

One day the kitchen changes "table number" from 12 to {"floor":1,"table":12}. The kitchen thinks the ticket is fine, but the stock-keeper can't read it and orders get lost.

EventGate is the manager at the printer. Before the new ticket format goes out, it asks every reader: "Can you still read this?" If anyone can't, the new format is stopped.

🛂

In one sentence (technical)

EventGate compares the old and new version of an event schema, checks the difference against what each downstream consumer declared it needs, runs environment rules (prod is strict, dev is lenient), and only publishes the event to Amazon EventBridge if the answer is ALLOW.

💬 Say this:"Normal schema checks ask: is this event valid for the producer? EventGate asks: which consumers break if we ship this, and should we ship it to this environment?"

02 Elevator pitches

Learn these almost word for word. Interviewers usually start with "Tell me about a project you built."

⏱️ 30-second version

"In microservices, one team changes an event and another team's service crashes in production, because nobody checked who depends on that field. I built EventGate, a consumer-aware release gate. Every consumer declares the fields it needs. When a producer proposes a new event version, EventGate diffs the schemas, checks each consumer with 8 deterministic rules, and returns ALLOW, REVIEW or BLOCK based on the environment. Only allowed events are published to EventBridge. It runs serverless on AWS with Lambda, API Gateway, DynamoDB and EventBridge, plus a React console, a CLI and a GitHub Actions check."

⏱️ 2-minute version (structure)

  1. Problem: producers change schemas on their own, and consumers break at runtime. Schema registries only check the producer's own schema.
  2. Idea: model consumers explicitly with consumer contracts so you know the exact blast radius.
  3. How: diff → per-consumer rules (EVT001–008) → SAFE/RISK/BREAK → environment policy → ALLOW/REVIEW/BLOCK → publish only on ALLOW → write an audit record.
  4. Engineering: hexagonal architecture (pure-Python domain, swappable JSON/DynamoDB storage and local/EventBridge publisher), FastAPI on Lambda via Mangum, IaC with SAM, least-privilege IAM, optional AWS Cedar policies.
  5. Proof: 279 backend tests (91.5% coverage), 114 frontend tests, a CI gate that fails PRs with breaking changes, live deployment.
  6. Next: auth, nested schemas, outbox pattern for audit consistency.

03 Basics you must know

If you're new to these words, read this first. Interviewers will use them.

📣 Event

A message saying "something happened", e.g. OrderPlaced. It's a fact in the past tense.

🏭 Producer

The service that sends the event (e.g. the Order service).

📥 Consumer

A service that listens and reacts (Billing, Inventory, Analytics).

🔀 Event-driven architecture

Services talk by sending events through a broker instead of calling each other directly. The upside is loose coupling. The downside is that it's easy to break someone you can't see.

📮 Message broker / event bus

The "post office" that delivers events to subscribers. Here that's Amazon EventBridge.

📜 Schema / contract

The agreed shape of an event: field names, types (string, number…) and whether each field is required.

📄 Event contract

The producer's schema, versioned (v1, v2…).

🧾 Consumer contract

What a consumer says it needs from an event, e.g. "I need shippingMethod as a string."

💥 Breaking change

A change that makes old consumers fail: removing a field they need, changing its type, or changing whether it's required.

🎯 Blast radius

Who gets hurt by a change. EventGate makes it precise: these consumers, this field, this rule.

☁️ Serverless

You upload code and AWS runs it on demand. You don't manage servers and don't pay for idle time (Lambda).

🧩 Hexagonal architecture

The business logic sits in the middle and has no idea about AWS or HTTP. Adapters plug in around it, like USB devices.

🏗️ Infrastructure as Code

Your cloud setup written as a file (template.yaml) so it's repeatable and reviewable.

🔑 Least privilege

Give each component only the exact permissions it needs and nothing more.

🎲 Deterministic

Same input, same output, every time. Important for a gate you need to trust.

04 The problem

A real-looking example taken from the repo's own fixtures (contracts/events/order-placed/).

Producer: OrderPlaced v1 → v3

// v1 (current)
"shippingMethod": { "type": "string", "required": true }

// v3 (proposed)
"shippingMethod": { "type": "object", "required": true }

Consumer: inventory-service

{
  "consumerId": "inventory-service",
  "eventType": "OrderPlaced",
  "expectedFields": {
    "orderId":        { "type": "string", "required": true },
    "items":          { "type": "array",  "required": true },
    "shippingMethod": { "type": "string", "required": true }
  }
}

Without a gate 😱

  1. Producer validates the payload against its own v3 schema, and it passes.
  2. The event is published to the broker.
  3. inventory-service expects a string and gets an object. It throws a type error and order fulfilment fails in production.

With EventGate 🛡️

  1. EventGate sees that shippingMethod changed from string to object.
  2. inventory-service depends on it, so rule EVT001_FIELD_TYPE_CHANGED fires: BREAK HIGH.
  3. Billing and Analytics don't use that field, so they stay SAFE. That's precise, not a false alarm.
  4. Decision BLOCK, HTTP 409. EventBridge is never called. No consumer ever sees the bad event.

05 What EventGate does (9 steps)

This is the core pipeline. Memorize the order.

  1. Load contracts: the current and proposed event versions, plus every consumer contract for that event type.
  2. Compute a structural diff (compute_change_set): added fields, removed fields, type changes, requiredness changes.
  3. Check each consumer: only changes to fields that consumer declared matter (consumer scoping).
  4. Compatibility result: apply rules EVT001–EVT008, giving SAFE / RISK / BREAK.
  5. Severity: LOW / MEDIUM / HIGH. Any BREAK → HIGH, any RISK → MEDIUM, otherwise LOW.
  6. Apply environment policy: production, staging or development (Standard Python engine or AWS Cedar).
  7. Release decision: ALLOW / REVIEW / BLOCK.
  8. Gated publish: call events:PutEvents only if ALLOW. Otherwise stop with HTTP 409.
  9. Record history: save an audit record linking analysisId, requestId, decision and the EventBridge event ID.

    07 The two-level decision model

    This is the most important design idea. Interviewers love it because it shows separation of concerns.

    Level 1: Compatibility (a fact)

    "What is the technical impact of this change?"

    Status: SAFE RISK BREAK
    Severity: LOW MEDIUM HIGH

    The same input always gives the same result. It doesn't care about the environment.

    Level 2: Release policy (a choice)

    "Given that impact and this environment, what should we do?"

    Decision: ALLOW REVIEW BLOCK

    Depends on risk tolerance: dev can accept a medium risk with a warning, prod can't.

    💬 Say this:"Compatibility describes the impact. Policy decides the action for the environment. Keeping them separate means I can change governance rules, or swap in AWS Cedar, without touching the compatibility engine."

    Aggregation rule (from domain/decision.py)

    Findings across all consumers Compatibility Severity
    Any finding is BREAK BREAK HIGH
    No BREAK but at least one RISK RISK MEDIUM
    All SAFE SAFE LOW
    No consumers registered at all RISK MEDIUM
    💡 Smart detail: the empty consumer set"We don't know who uses this" must never silently become ALLOW. If nobody is registered, EventGate can't prove safety, so it says RISK/MEDIUM. That means REVIEW in prod and staging (dev allows it with a warning). It's a "fail-safe" default.

    08 The 8 compatibility rules

    Defined in backend/src/eventgate/domain/compatibility.py. Lower precedence number = higher priority.

    # Rule ID Simple meaning Result
    1 EVT001_FIELD_TYPE_CHANGED A field this consumer uses changed to an incompatible type (string → object). BREAK HIGH
    2 EVT003_CONSUMER_REQUIRED_FIELD_MISSING The consumer requires a field that's gone from the new version. BREAK HIGH
    3 EVT002_REQUIRED_FIELD_REMOVED Producer removed a field that used to be required. (Reserved in the precedence table; see limitations.) BREAK HIGH
    4 EVT004_REQUIREDNESS_CHANGED A field the consumer uses flipped required ↔ optional. BREAK HIGH (in current code)
    5 EVT007_UNSUPPORTED_CHANGE A change outside the supported patterns. (Reserved.) BREAK HIGH
    6 EVT006_OPTIONAL_FIELD_REMOVED Removed a field the consumer marked as optional. It might still use it. RISK MEDIUM
    7 EVT005_OPTIONAL_FIELD_ADDED A new optional field was added and this consumer doesn't care. SAFE LOW
    8 EVT008_CONSUMER_UNAFFECTED Nothing this consumer uses changed. SAFE LOW

    🎯 Consumer scoping

    A change only creates a finding for a consumer if that consumer declared the field. This is what removes false alarms.

    🧹 Deduplication

    If several rules hit the same consumer + same field, only the highest-priority one is kept (_deduplicate_findings). One clear reason per field.

    🔢 Type widening

    Only an explicit allow-list is compatible. Same type → same type, plus integer → number (every integer is a number). Anything unknown counts as incompatible, so it's safe by default.

    💡 Determinism trickFindings are sorted by consumer, field, precedence and ruleId. The same input gives byte-identical output, which makes tests, CI and audit reports reliable.

    09 Release policy & AWS Cedar

    Two pluggable engines behind one interface, IPolicyEngine. You pick one with the env var EVENTGATE_POLICY_ENGINE=standard|cedar.

    Environment LOW (SAFE) MEDIUM (RISK) HIGH (BREAK)
    production ALLOW REVIEW BLOCK
    staging ALLOW REVIEW BLOCK
    development ALLOW ALLOW + warning BLOCK

    🐍 Standard engine

    StandardReleasePolicyEngine: plain Python if/else that implements the matrix above. Fast, simple, no dependencies.

    🌲 Cedar engine

    CedarReleasePolicyEngine evaluates policies/release_policy.cedar with cedarpy. Cedar is AWS's open-source policy language (used by Amazon Verified Permissions). The principal is the Environment, the action is "Release", and severity goes in the context. 

    // policies/release_policy.cedar (excerpt)
@id("PROD_BLOCK_BREAK")
forbid (principal, action == Action::"Release", resource)
when { context.severity == "HIGH" };

@id("DEV_ALLOW_WARNING")
permit (principal == Environment::"development", action == Action::"Release", resource)
when { context.severity == "MEDIUM" };
    💬 Why Cedar?"Policy as code. A governance or platform team can read and change release rules in a small, formal, analyzable language without editing Python. In Cedar, forbid always beats permit, so 'block HIGH everywhere' can't be overridden by accident."
    ⚠️ No silent fallbackIf you configure cedar and the policy file or cedarpy is missing, it raises ConfigurationError instead of quietly using the standard engine. A gate should fail loudly.

    1. Generate a unique event_id (UUID).
    2. Load the proposed contract and validate the real payload against it: required fields present, types correct. A bad payload means 422 before any heavy work.

    14 Data model (DynamoDB)

    In DynamoDB you design keys around your access patterns, not around entities.

    📄 event-contracts

    • PK eventType (S)
    • SK version (N)
    • Get one version: GetItem(eventType, version)
    • All versions: Query(eventType)
    • Catalog item: eventType="METADATA#CATALOG", version=0

    🧾 consumer-contracts

    • PK consumerId (S)
    • GSI EventTypeIndex: eventType + consumerId
    • "Who consumes OrderPlaced?" → Query the GSI
    • Catalog item: consumerId="METADATA#CATALOG"

    📒 release-history

    • PK recordId (= analysisId)
    • GSI EventTypeIndex: eventType + timestamp
    • Timeline per event type, newest first
    • Stores decision, severity, published, eventBridgeEventId, affected consumers
    💡 "Zero-scan" catalog patternA Scan reads the whole table, which is slow and costly. Instead, a single catalog item (METADATA#CATALOG) keeps the list of all event types and consumer IDs, so "list everything" is one GetItem. Trade-off: the catalog item must be updated on every write and is capped by DynamoDB's 400 KB item size limit.

    17 CLI & CI gate ("shift left")

    Catch breaking changes in the pull request, long before production.

$ eventgate check --event OrderPlaced --current 1 --proposed 3 --env production

REVIEW (Severity: MEDIUM)    # exit 1 (exit 2 without the flag)

    🤖 GitHub Actions: eventgate-contract-check.yml

    1. Triggers on any PR that touches contracts/** (or a manual dispatch).
    2. scripts/ci_contract_diff.py finds the changed contracts against the base branch.
    3. Runs the check for production with --fail-on-review.
    4. A non-zero exit code fails the PR, so the merge is blocked. The result is written to the job summary.

    19 Security & failure handling

    🔐 Security in place

    • Least-privilege IAM: read-only GetItem/Query on the contract tables, GetItem/PutItem/Query on history, and events:PutEvents only on the one bus ARN. No wildcard data permissions.
    • Consumer Lambdas can only be invoked by EventBridge from that specific rule (SourceArn).
    • Request ID sanitized (alphanumeric, -, _, max 128 chars) to prevent log injection.
    • Boundary validation: bad input → 422 before the domain runs.
    • No secrets in the repo.

    🧯 Failure handling

    • Malformed payload → 422 INVALID_EVENT_PAYLOAD
    • Missing contract or record → 404
    • Breaking or risky publish → 409 EVENT_PUBLISH_BLOCKED
    • EventBridge down → 503 EVENTBRIDGE_UNAVAILABLE
    • Unknown exception → a uniform error envelope with requestId
    • Demo consumers never re-publish, which prevents event loops

    21 Honest limitations & what I'd improve

    These were checked against the code. Bringing up weaknesses yourself shows ownership and depth, which interviewers respect a lot.

    1. No API authentication

    The HTTP API has no authorizer and CORS is *. Fix: Cognito/JWT or IAM auth on API Gateway, a narrower CORS origin, and WAF throttling.

    2. The bus can be bypassed

    Any principal with PutEvents could publish directly. Fix: an EventBridge resource policy that allows only EventGate's role to put events on the bus, so the gate is the only door.

    3. Publish and audit aren't atomic

    The event is published first, then history is written. If that write fails, it's only logged as a warning. Fix: the transactional outbox pattern, or write a PENDING record first and then update it.

    4. Top-level schemas only

    payload_validator and the diff look at top-level fields. Nested objects and array element types aren't compared. Fix: recursive diff using paths like shipping.method, or full JSON Schema.

    5. EVT004 is conservative

    Any requiredness change on a consumed field is BREAK/HIGH. But optional→required is actually safer for consumers. Fix: required→optional = BREAK (if the consumer requires it), optional→required = SAFE.

    6. EVT002 & EVT007 are reserved

    They're in the precedence table but the engine doesn't emit them today. Removals are caught through consumer-scoped EVT003/EVT006. That's on purpose (no consumer, no finding), but the docs list them as active.

    7. Trust in self-declared contracts

    If a consumer's contract is stale, the gate is wrong. Fix: consumer-driven contract tests (Pact-style) in each consumer's CI, or generate contracts from consumer code.

    8. Single region, demo scale

    One stack in ap-south-1 with cold starts. Fix: provisioned concurrency for the API, DynamoDB global tables and multi-region buses if needed.

    22 Scaling & system-design follow-ups

    📈 "What if there are 10,000 event types and 1,000 consumers?"

    • The engine costs O(changed fields × consumers of that event), not all consumers, because of the GSI query by eventType.
    • Lambda scales out horizontally. DynamoDB on-demand absorbs spikes.
    • Cache contracts in Lambda memory (warm container) with a short TTL, or add DAX.
    • Shard the catalog item (or paginate it) to stay under 400 KB.
    • Split analyze (read-heavy) from publish (write path) if needed.

    ⚡ "What about high event throughput?"

    • The contract check needs to run once per version change, not once per event. In production, validate the schema version at deploy time and cache the decision, keeping only cheap payload validation per event.
    • Batch PutEvents (up to 10 entries per call) and watch EventBridge regional quotas.
    • Add DLQs and retries on consumer targets.

    🌍 "Multi-team governance?"

    • Contract ownership per team (owner field), CODEOWNERS on contracts/.
    • A REVIEW workflow: approvals recorded in history, then a re-publish.
    • Notify affected consumer teams (Slack, SNS) automatically.

    🔭 "Observability?"

    • Already has: requestId propagation and structured logs.
    • Add: X-Ray tracing, CloudWatch metrics (blocks per day, top breaking fields), alarms on 5xx and EventBridge failures.

    23 How is it different from existing tools?

    Tool What it checks Gap EventGate fills
    Confluent / AWS Glue Schema Registry New schema vs old schema under a generic mode (BACKWARD, FORWARD, FULL) Producer-only. Doesn't know which consumers use which fields, so it gives false alarms or misses context.
    EventBridge Schema Registry Discovers schemas and generates code bindings No enforcement or release gate
    Pact (consumer-driven contracts) Consumers publish expectations, providers verify them in CI EventGate pairs this idea with runtime gating at the broker, environment policy and an audit trail
    JSON Schema validation One payload vs one schema No version diff, no consumer view, no decision
    💬 One-liner:"Schema registries protect the schema. EventGate protects the consumers, and enforces that at the point of publishing."

    Any BREAK → HIGH. Any RISK → MEDIUM. All SAFE → LOW. No consumers → MEDIUM.

    HIGH → BLOCK everywhere. MEDIUM → REVIEW (prod/staging), ALLOW + warning (dev). LOW → ALLOW.
